# Patch fork of SEO Playground

Fork of [paulmassen/seo-playground](https://github.com/paulmassen/seo-playground), deployed on Railway as the Semrush Map Rank Tracker replacement.

## Changes from upstream

- **Monthly Geo-grid schedules** (`Every month` + day 1-28) alongside daily/weekly. The day of month is stored in the existing `weekday` column, so no schema change.
- **Password protection** (`src/middleware.ts`): HTTP basic auth on every page. Username `SITE_USERNAME` (default `patch`), password `SITE_PASSWORD`. Without `SITE_PASSWORD` the app returns 503.
- **Daily upstream sync** (`.github/workflows/sync-upstream.yml`): merges upstream `main` into this fork; Railway redeploys on the push.
- **Semrush MRT parity for maps**:
  - Radius in miles (`Radius (miles)`, 5 mi default, 10 mi for rural), stored as km between points. New monitors default to 9x9, Standard queue.
  - Scheduled scans run in the **clinic's** time zone (looked up from the map center), defaulting to the 15th at 12:00. "Scan monthly" on the setup form is **unticked** by default (changed Nov 20 2026), so a scan is only scheduled when someone ticks it.
- **Default Project = one-time scans only** (sales demos; added Nov 20 2026). Project ID `default` can never hold a schedule: the old Geo-Grid screen hides the monthly box and the schedule control there, `saveGridSchedule` (`src/lib/db.ts`) refuses it, and the worker skips any schedule found there. Rule lives in `src/lib/grid-guardrails.ts`.
- **Project check on the old Geo-Grid screen** (`/dashboard/geo-grid`): the active project is one server-wide setting, so the form shows "Saving to: <project>" and posts the project it was opened with. If the active project changed since, the scan is refused ("The selected project changed to …") before any DataForSEO call. Scan links without `project_id` are refused too.
  - A point outside the top 20 shows as a red **20+** (like Semrush). A grey **—** / "No data" means DataForSEO failed at that point: failed tasks are re-posted up to 3 times before a point is marked `failed`.
  - **Organic-only ranks** (Nov 2026): ads (`is_paid`) are dropped and the organic listings renumbered 1..N, so an ad no longer pushes the client down and the client is never matched on its own ad. Tasks request `depth: 30` (about $0.0018 a point instead of $0.0012) so ~20 organic listings remain after ads; only organic 1-20 are stored, so the UI, visibility and MRT (21 = unranked) are unchanged. Each listing keeps DataForSEO's own `provider_rank` and `rank_absolute`, and its `place` ("City, ST") when Google shows one. If ads used up the depth before 20 organic listings came back (`truncated`) and the client isn't among them, its rank is unknown: `rank: null, rank_unresolved: true`, left out of MRT like a failed point.
  - **Wrong-city check** (Nov 2026; `src/lib/grid-location-check.ts`). On Nov 15 2026 DataForSEO/Google intermittently answered correct requests with national result pages (clinics in Tulsa, Albuquerque, Henderson) at 2,680 of 22,853 points. Every result is now checked: a point is wrong-city if **any of its top 5 organic listings is more than 150 km** from the grid point. A listing is placed by the "City, ST" in its description using a bundled Census 2023 gazetteer (places, then towns/townships, then counties: `src/lib/data/us-places.json`, rebuilt with `scripts/build-us-places.mjs`); a name that's ambiguous in its state, or unknown, falls back to the state's center with a 900 km threshold. A wrong-city point is never stored as ranks: it is re-posted 5 min later, then 30 min after that (bursts lasted minutes), and if the 3rd search is still wrong-city it's stored as failed with `failed_reason: "wrong_city"` and the evidence (`rechecks[]`: task_id, check_url, far listings). Task errors, malformed results and tasks pending 30+ min are re-posted at once. There are no per-monitor exceptions. If none of a point's top 5 can be placed (e.g. all show a street address, which in practice means local results), it's kept and counted as `location_status: "unresolved"`. Validation against the Nov 15 archive: `npx jiti scripts/check-wrong-city-archive.mjs <investigation dir>` (the archive isn't committed).
  - Every point keeps its DataForSEO `task_id` and Google `check_url`, and tasks carry a `tag` (`<monitor id>|r<row>c<col>`) so a run's tasks can be found in DataForSEO's free `id_list`. `DATAFORSEO_BASE_URL` (default `https://api.dataforseo.com`) redirects the Geo-grid calls only, for local testing against a mock.
  - The monitor list shows every monitor (upstream capped it at the newest 100 runs).
  - At most `GEO_GRID_MAX_CLAIMS_PER_PASS` (default 20) scheduled monitors start per worker pass (one pass a minute), so hundreds of monitors on the 15th start in waves; task polling is capped at 10 requests in flight per run.
  - **Retention is OFF by default** (changed Oct 28 2026): no map scans are deleted, so the imported Semrush history and every new client's history are kept. Code is in `pruneGridHistoryForProject` (`src/lib/db.ts`), called from `src/app/api/cron/geo-grid/route.ts`. Set `GRID_RETENTION_ENABLED=true` on the `app` service to turn it on; no code change needed. When on, it runs once a day and on the first worker pass after every app restart (the timer is in memory), and each monitor keeps its starting-point run (the `pinned` run, else its oldest finished run) plus the last ~6 months; older finished runs are deleted. Pending and failed runs are never touched. Before enabling, make sure each monitor's intended baseline scan is pinned (see `PATCH /runs/{run_id}` below), or the oldest finished scan becomes the protected start. Intended long-term plan was starting-point scan + last 6 months, so enable it if storage ever becomes a concern.
- **Location-based Geo-grid pages** (`/dashboard/geo-grid/clients`, code in `src/lib/grid-locations*.ts` and `src/app/dashboard/geo-grid/clients/`): All clients → client → location → keyword, with Add client / location / keyword, Run now, Settings and a one-time Sales demo scan (Default Project, Standard queue, never scheduled). The sidebar's **Geo-Grid Ranking** opens these pages. The old one-off screen (`/dashboard/geo-grid`) is out of the menu, but its URL and every link to a scan result still work.
  - A location is derived from existing monitors (project + CID or target + center rounded to 4 decimals), so there is no schema change. The center is part of each keyword's series, so a clinic that moves is added again as a new location.
  - Every URL carries the project ID, checked on the server. These pages never read or change the active project.
  - A new location or keyword scans right away (`next_run_at` = now); that first scan is its starting point, and the worker then moves it to its regular scheduled slot.

## Railway

- `app` service: builds this repo's Dockerfile, volume at `/data`, vars `DB_PATH=/data/seo-playground.db`, `CRON_SECRET`, `SITE_PASSWORD`, `RAILWAY_RUN_UID=0` (volume is root-owned; the image runs as uid 1001). Optional: `GRID_RETENTION_ENABLED=true` (see Retention above), `GEO_GRID_ALERT_WEBHOOK_URL` (secret; Slack incoming webhook for #seo-workflow-errors, see Alerts below).
- `worker` service: same repo, start command `node scripts/geo-grid-worker.mjs`, vars `CRON_SECRET` (same value), `GEO_GRID_WORKER_URL=http://app.railway.internal:3000`. No volume, no public domain.
- Volume backups are scheduled on the `app` volume.
- Storage: the volume (`seo-playground-data`) is 50 GB. It sat near 0 until the Semrush history import (Oct 2026), then jumped to roughly 6 GB. Check Railway → project → volume card → Metrics. SQLite does not shrink its file after deletes, so turning retention on later will stop growth rather than free space. Volumes can be enlarged in Railway if needed.

## Reporting API

All requests need `x-api-key: <REPORTING_API_KEY>` (or `Authorization: Bearer <key>`). Covers every project.

- `POST /api/v1/geo-grid/monitors` : creates a monitor **without running a scan** (no DataForSEO cost). Body:
  `{ keyword, business: { name, cid }, center: { lat, lng }, grid_size?: 9, radius_mi?: 5 | spacing_km?, language?: "English", project?: "<project id>" | { name, domain }, schedule?: { day_of_month?: 15, time_of_day?: "12:00" } | false, runs?: [{ run_at, pinned?, points: [{ row, col, lat?, lng?, rank }] }] }`.
  A `project` object files the monitor under that client's project, matched by website domain and created on first use (one project per clinic website, so multi-location clinics share one).
  With no `project`, the monitor goes to the first project, usually the Default Project, which only takes one-time monitors: send `schedule: false` there, or the call returns 400 and writes nothing.
  `runs[]` imports past scans (e.g. from Semrush MRT); ranks above 20 are stored as "20+". `pinned: true` marks the starting-point scan. Repeating the call for the same location and scan dates does not create duplicates.

- `GET /api/v1/geo-grid/monitors` : all monitors (including scheduled ones with no runs yet) with schedule and latest completed run summary. Filters: `?cid=`, `?q=` (keyword/target text), `?project=`.
- `DELETE /api/v1/geo-grid/monitors/{monitor_id}` : removes a monitor (all snapshots and its schedule) from every project, or only `?project=`.
- `PATCH /api/v1/geo-grid/runs/{run_id}` with `{ "pinned": true }` : makes that run the monitor's one starting-point map (other pins in the monitor are cleared); `{ "pinned": false }` unpins it. The starting-point map should be the scan closest to the client's SEO start date, and it must match what the reporting agent has pinned. Find run IDs with `GET .../monitors/{monitor_id}/runs`.
- `GET /api/v1/geo-grid/monitors/{monitor_id}/latest` : newest completed run with every grid point.
- `GET /api/v1/geo-grid/monitors/{monitor_id}/runs` : run history (summaries only).
- `GET /api/v1/geo-grid/runs/{run_id}` : one run with every grid point.

Run payload:
- Each run has `pinned` (starting-point scan).
- `points[]`: `row`, `col`, `lat`, `lng`, `rank` (null = not in top 20) and `results` (that point's top 20: rank, title, domain, cid, rating, reviews, is_target). `?competitors=false` drops `results`.
- `positions[]`: Semrush MRT heatmap shape, `{ point: { id, coordinates: { lat, lng } }, position?, diff? }`; `position` is omitted when not in the top 20 and `diff` is vs the previous run (negative = improved).
- `top_competitors[]`: business (cid, name, domain, rating, reviews), `average_position`, `share_of_voice`, `found_points`, `is_target`.
- `business`: `{ cid, name, coordinates }` (the pin) and `summary`: `visibility` (0-100 share of voice), `average_rank` (found points only), `top3`, `found`, `total`, and `mrt_average_position` (Semrush MRT's rule: every point counts, outside the top 20 = 21, failed points left out).

Data quality (Nov 2026, additive):
- Points add `task_id`, `check_url`, `failed`, `failed_reason` (`wrong_city` | `task_error` | `timeout`) and `rank_unresolved`.
- Run headers add `quality: { points, failed_points, wrong_city_failed, unresolved_points, rank_unresolved_points, wrong_city_rechecks }`, `rescanned_at` (set when a re-scan replaced the run's points; the run's date is unchanged) and `report_safe` / `report_safe_reason`. The rule is **fail loudly**: anything unknown or unfinished is `null`, never `true`.
  - `report_safe: true`: every point was checked by the wrong-city code and the run passed.
  - `report_safe: false` + `report_safe_reason`: **not safe to report**. Reasons: `wrong_city_persistent` (any wrong-city failed point), `incomplete_grid` (not exactly one point per row/col of the grid), `too_many_failed` (more than 2 failed points), `rank_unresolved` (a truncated point where the target's rank is unknown), or a re-scan reason: `pending_rescan`, `excluded_from_rescan`, `original_restored`, or a hold reason below.
  - `report_safe: null`: unknown. `report_safe_reason: "not_checked"` for a finished run the wrong-city check never saw (every run before Nov 2026, Semrush `import-*` runs, Nov 15 runs not re-scanned yet: a non-failed point without `raw_count`). A known problem wins over `not_checked` (e.g. an old partial grid is `false`, `incomplete_grid`). A run that isn't finished (pending/failed) is `null` with no reason.
  - A re-scan's stored flag always wins over the computed one.
  - Every endpoint shows the same flag: `runs/{run_id}`, the monitors list (on the monitor and its `latest_run`), `/latest` and `/runs`. A monitor carries its **latest finished run's** flag.
- Unsafe runs are not hidden: the CS OS sync still carries their numbers. `GET /api/v1/geo-grid/rescans?unsafe=true` is the "not safe to report" list: `{ unsafe: [...], not_checked_runs }`. `unsafe[]` has every run flagged by a re-scan (`source: "flag"`) **and** every finished run with no flag whose points make it unsafe (`source: "computed"`; scheduled, manual or live; any project), each with `reason` and `evidence` (its failed and rank-unresolved points: row, col, reason, task_id, check_url, rechecks). `not_checked_runs` counts the finished runs that are `null` / `not_checked` (they aren't listed).

Run history adds `metrics: { average_positions, share_of_voices, mrt_average_positions }` keyed by ISO date, like Semrush MRT. `mrt_average_positions` is what the CS OS map pack sync (n8n "CS OS — Sync SEO Playground Map Pack (Daily)") stores, so its numbers line up with the Semrush-era history. The monitor list's `project` also carries `domain`.

## Re-scans (temporary, Nov 2026)

`/api/v1/geo-grid/rescans` re-scans finished runs **in place** to replace the Nov 15 2026 wrong-city data. Delete the route (`src/app/api/v1/geo-grid/rescans/`) and the worker call in `src/app/api/cron/geo-grid/route.ts` when it's no longer needed; the `grid_rescan*` / `grid_run_safety` tables are harmless (but keep `runSafety` for scheduled runs).

How it works:
- The run stays `done` with its current points while new tasks are posted at its **own** point coordinates (standard queue) and collected on the side by the worker. One transaction swaps the new points in; the old points are kept for undo. The run's `ts` (its date) never changes; `rescanned_at` is set. The CS OS sync upserts by date, so the corrected value overwrites the old one at its next 9am run.
- A run is swapped only if: every point is present exactly once, **no** wrong-city point is left, at most 2 points failed for other reasons, no submission's outcome is unknown, and the run's points and settings (keyword, target, center, grid, spacing, language) are unchanged since the attempt began. Otherwise it's **held** with a reason (`wrong_city_persistent`, `too_many_failed`, `incomplete`, `post_unknown`, `budget_exhausted`, `timeout` (attempt over 2 h), `source_changed`, `bad_source`) and the old points stay live, flagged not safe to report. Held runs are retried by an operator, never automatically.
- **Billing safety:** every POST is recorded in `grid_rescan_submissions` (tag `rs:<run_id>:a<attempt>:r<row>c<col>:s<seq>`) *before* it's sent and resolved after. A submission with no outcome after 10 min (crash mid-POST), or a POST that timed out, is `unknown`: that point is never re-posted automatically and the run is held `post_unknown`; reconcile its tag with DataForSEO's free `id_list` before retrying. Each point gets at most 3 accepted searches (initial, +5 min, +30 min after the previous); DataForSEO rejections are retried up to 3 times, 1 min apart.
- **Spend ceiling:** one budget shared by all re-scans (`GEO_GRID_RESCAN_BUDGET_USD`, default $60, settable via `action: "budget"`). Each submission reserves `GEO_GRID_RESCAN_TASK_PRICE_USD` (default $0.0018) before it's posted; when the budget is full, nothing more is posted and affected runs are held `budget_exhausted`.
- **Pacing:** at most `GEO_GRID_RESCAN_MAX_STARTS_PER_PASS` (default 10) runs start per worker pass, across all projects.

API (same `x-api-key`):
- `POST { action: "preview", date: "2026-11-15", run_ids? | monitor_ids? | all?: true, exclude_monitor_ids?, label? }` (the default action): lists the runs it would re-scan, the excluded and skipped ones, the points and the estimated cost, and saves that list as an immutable manifest (`manifest_id`). The date is the run's date in its clinic's time zone (UTC if the monitor has no schedule). Finished runs only; imported runs and runs already queued/scanning/swapped are skipped. Changes nothing else.
- `POST { action: "start", manifest_id }`: queues exactly that manifest. Max **25** runs unless the preview used `all: true`. Queued runs are flagged `pending_rescan` (not safe) until they swap; excluded runs on that date are flagged `excluded_from_rescan`.
- `POST { action: "cancel" | "undo" | "retry", run_ids }` (max 25): cancel a queued/scanning re-scan; undo a swap (restores the old points, refused if the run changed since); retry a held/cancelled/undone run as a new attempt (old attempts are kept).
- `POST { action: "exclude" | "unexclude", monitor_ids, reason? }`: the persistent exclude list (e.g. The Mobility Project, `grid-2d62872a`, whose grid is centered in the Nevada desert).
- `POST { action: "budget", limit_usd }`.
- `GET ?label=&state=&manifest_id=`: counts by state, the budget, and per run: state, hold reason, points collected/pending, wrong-city detections and points left, failed points, old → new `mrt_average_position`, searches and cost; plus every wrong-city detection (task_id, check_url, far listings). `GET ?unsafe=true`: the "not safe to report" list with reason and evidence, plus `not_checked_runs` (see Data quality above).

Submission outcomes (Codex round 3): a POST counts as **rejected** (safe to re-post) only on HTTP 4xx, HTTP 200 with a top-level DataForSEO status of 40000+ and no tasks, or a task in the answer with a status of 40000+. HTTP 5xx, a network error or timeout, a body that isn't JSON, no `tasks` array, or a task missing from the answer are **unknown** (held `post_unknown`, never re-posted). Re-scans always post to the standard queue (priority 1), since the budget reserves the standard price. A run left in `posting` for 10+ min with nothing in flight (a crash between claiming it and finishing its POSTs) is held `post_unknown` with its ledger (tags and states) as evidence. Every state change and its safety flag are written in one transaction (start, cancel, hold, undo, swap). A cancel or retry that lands while a re-scan is posting stops it: the attempt is re-checked in the same transaction as each submission's intent.

Scheduled runs: a task DataForSEO refused at the first post is kept as a retry-pending point and re-posted after 60 s (up to 3 refusals, then failed `task_error`). If no task at all was accepted, no run is created and the slot is retried every 5 min, but only within 6 h of the **original** slot (`grid_schedules.retry_slot_at` carries it across retries; before Nov 2026 the window restarted at every retry, so a failing slot retried until the next month). If that start got an **unclear** answer (timeout, 5xx, odd body: DataForSEO may have queued and billed the tasks without us getting their ids), the slot is retried **once** (`grid_schedules.unclear_posts`), then stopped until the next slot; both are alerted. This one-retry policy is a judgment call (a possible second charge vs. a missing month) and can be changed in `MAX_UNCLEAR_SLOT_POSTS` (db.ts). Run now, saving a schedule or changing its settings clears the retry chain. A task with an unclear outcome inside a partly accepted start is not re-posted, so the run finishes incomplete and is flagged `incomplete_grid`. A single-point re-post with an unclear answer is still re-posted later (capped at 3 attempts per point) and alerted. Task answers are matched to requests by the `tag` DataForSEO echoes back (`data.tag`); without tags, by position only when the counts match, otherwise unknown. `items: null` from DataForSEO is a task error (re-posted), not "not in the top 20"; only `items: []` is a real zero-result search.

## Alerts

`src/lib/grid-alerts.ts`. Every alert is logged as one line, `[geo-grid-alert] {json}`, in the `app` service logs. If `GEO_GRID_ALERT_WEBHOOK_URL` is set, it is also posted to Slack as `{ text }` (kind, reason, monitor/run/project ids), at most once per kind + run + monitor + reason per app process (a held run doesn't alert every pass; an undelivered post is retried on the next occurrence). The webhook URL is a Slack incoming webhook for **#seo-workflow-errors**. It is a **secret**: set it only as an env var on the Railway `app` service, never commit or log it. Without it, alerts go to the logs only.

Kinds:
- `rescan_held`: a re-scan was held (reason = the hold reason, e.g. `post_unknown`, `wrong_city_persistent`, `budget_exhausted`).
- `posting_stalled`: a re-scan stayed in `posting` for 10+ min with nothing in flight; held `post_unknown`.
- `rescan_error`: one re-scan's worker step threw; its state is unchanged and it's tried again next pass. Also counted in the worker response (`rescans.errors`).
- `scheduled_run_unsafe`: a scheduled or manual queued run finished, but its points aren't safe to report (reason as for `report_safe_reason`).
- `price_mismatch`: DataForSEO billed an accepted re-scan task more than 1% over `GEO_GRID_RESCAN_TASK_PRICE_USD`, or reported no cost for it.
- `scheduled_start_unclear`: a scheduled run's start got an unclear answer and may have been billed. Reason `unclear_post_retrying` (retried once in 5 min), `unclear_post_stopped` (no run this slot; re-run by hand after checking DataForSEO's free `id_list` for the monitor's tags), `unclear_post_partial` (some tasks accepted; the run will finish incomplete) or `start_error` (a local failure after posting).
- `scheduled_start_failed`: a scheduled run's start was refused and its 6 h retry window is used up (reason `retry_window_used`); no run this slot.
- `scheduled_repost_unclear`: a scheduled run's single-point re-post got an unclear answer (possible second charge for that point).
- `rescan_post_unknown_unheld`: a re-scan POST got an unclear answer, but a cancel or retry had already moved the run on, so it couldn't be held; the tags are in the alert.

The worker response also adds `gridCollectErrors` (scheduled/manual runs whose collection threw locally; each is logged with its run id), and each schedule that didn't start cleanly is logged with its monitor id and reason.
